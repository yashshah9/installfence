# v0.2 Next-Phase Roadmap — installfence

**Status:** v0.2.0 shipped (violations, hide-env, require-sandbox, darwin stub); PATH shims and package matrix still open  
**Target Version:** 0.2.0 – 0.6.0  
**Owner:** Yash Shah  
**Last Updated:** 2026-08-19  

---

## 1. Executive Summary

Evolve installfence from a **Linux-only bubblewrap wrapper** into a **cross-platform, observable package-install firewall**: report sandbox violations, support macOS, intercept package managers transparently via PATH shims, validate against a top-100 package matrix, and integrate with npm 12 install-script allowlists.

## 3. Milestone Breakdown

### Milestone M1 — Violation Reporting (v0.2.0)

**Goal:** Surface blocked file access, network attempts, and policy denials as structured events; enable CI to fail on violations.

#### Deliverables

- [x] `internal/violations/` — violation types, collector, JSON/text formatters
- [ ] Parse bubblewrap stderr / audit hook for denied operations (e.g., `--seccomp` or bind-mount failures)
- [x] `--json-violations` flag — emit NDJSON violation stream on stderr
- [x] `--fail-on-violation` flag — exit code 42 (or documented code) when any violation recorded
- [x] Enforce `hide_env_keys` — scrub via process env + bwrap `--unsetenv`
- [x] `--require-sandbox` — error instead of passthrough when bwrap missing
- [x] Unit tests for violation collector and bwrap arg mapping
- [x] Integration probe: `GITHUB_TOKEN` hidden inside privileged bwrap (SSH path audit still open)

#### Acceptance Criteria

| # | Criterion | Verification |
|---|-----------|--------------|
| AC1 | Blocked read of hidden path produces ≥1 violation record | Integration test in Docker |
| AC2 | `--fail-on-violation` exits non-zero when violation occurs | CI test |
| AC3 | `--json-violations` output is valid NDJSON, one object per line | Unit test + manual |
| AC4 | `--require-sandbox` exits 1 with clear message when bwrap absent | Manual on macOS |
| AC5 | `hide_env_keys` entries are not visible inside sandbox | `env` probe test |

#### Dependencies

- bubblewrap ≥ 0.6 with seccomp support (distro-dependent)
- Linux CI runner with bwrap installed

#### Risks

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| bwrap does not emit parseable violation messages | Medium | Add optional `--seccomp` profile with explicit deny rules + custom log |
| False positives on legitimate compiler reads | Medium | Document policy exceptions; per-path allowlist in YAML v0.3 |
| Performance overhead from violation capture | Low | Buffer stderr async; cap violation list at 1000 entries |

**Estimate:** 1.5–2 weeks

### Milestone M2 — macOS sandbox-exec Backend (v0.2.0)

**Goal:** Provide equivalent sandboxing on macOS using `sandbox-exec` with SBPL policy generated from the same YAML policy file.

#### Deliverables

- [x] `sandbox-exec` runner (runtime GOOS, not build tags yet)
- [ ] `internal/sandbox/linux.go` — refactor existing bwrap code behind build tag
- [x] Shared `Run()` / `RunWithOptions()` in `internal/sandbox/runner.go`
- [x] Minimal SBPL profile from `Policy` (hide paths, network deny)
- [x] `installfence health` reports bubblewrap / sandbox-exec availability
- [ ] CI job on `macos-latest` (passthrough + dry-run tests; sandbox-exec smoke where permitted)
- [x] Document macOS limitations (best-effort Seatbelt; Linux bwrap needs Docker `privileged`)

#### Acceptance Criteria

| # | Criterion | Verification |
|---|-----------|--------------|
| AC1 | `installfence pip install` uses sandbox-exec on macOS when available | Manual + macOS CI |
| AC2 | Same YAML policy file works on Linux and macOS (shared schema) | Cross-platform test |
| AC3 | Hidden paths inaccessible from sandboxed pip install test script | Integration test |
| AC4 | Graceful fallback documented when sandbox-exec denied (CI env restrictions) | README + health output |

#### Dependencies

- macOS 12+ with `sandbox-exec` available
- Xcode CLT for local dev builds

#### Risks

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| Apple deprecating `sandbox-exec` | Low | Abstract backend interface; evaluate `sandbox(7)` / Seatbelt alternatives |
| SBPL cannot express all bwrap rules | High | Document parity matrix; extend YAML with platform-specific overrides |
| CI macOS runners restrict sandbox-exec | Medium | Run structural tests + manual sign-off checklist |

**Estimate:** 2–3 weeks (parallel with M1 after platform refactor)

### Milestone M3 — Shell Shims PATH Intercept (v0.3.0)

**Goal:** Transparent interception — users type `pip install` and installfence wraps automatically without prefixing the command.

#### Deliverables

- [ ] `installfence shim install` — write shim scripts to `~/.installfence/shims/`
- [ ] `installfence shim uninstall` — remove shims and PATH hook
- [ ] Shim scripts for `pip`, `pip3`, `uv`, `npm`, `pnpm`, `yarn`
- [ ] Shell hook snippets for bash, zsh, fish (`eval "$(installfence shim env)"`)
- [ ] `--shim-policy PATH` — default policy for shim-invoked commands
- [ ] `installfence shim status` — list active shims and PATH order
- [ ] Integration test: shimmed `pip` invokes bwrap wrapper

#### Acceptance Criteria

| # | Criterion | Verification |
|---|-----------|--------------|
| AC1 | After `shim install`, `which pip` resolves to installfence shim | Shell test script |
| AC2 | Shimmed command passes through all original args unchanged | Arg preservation test |
| AC3 | `shim uninstall` restores original PATH resolution | Before/after `which` test |
| AC4 | Works in bash and zsh (documented fish support) | CI shell matrix |

#### Dependencies

- M1 `--require-sandbox` recommended for shim safety
- M2 for macOS shim parity

#### Risks

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| PATH ordering conflicts with pyenv/nvm | High | Document ordering; `shim status` diagnostic |
| Users forget shims are active | Medium | Prominent `health` + `shim status` output |
| Virtualenv pip bypasses shims | Medium | Document venv activation order; optional venv post-install hook (future) |

**Estimate:** 1–1.5 weeks

### Milestone M4 — Top-100 Package Compatibility Matrix (v0.4.0)

**Goal:** Automated regression suite proving installfence works with the most-installed packages across pip, uv, and npm ecosystems.

#### Deliverables

- [ ] `tests/compat/matrix.yaml` — 100 packages with ecosystem, version pin, expected exit code
- [ ] `tests/compat/run_matrix.sh` — orchestrator (parallel installs, timeout, retry)
- [ ] GitHub Actions workflow `compat.yml` — weekly + manual dispatch (Linux + bwrap)
- [ ] Compatibility badge / summary table in README (auto-generated)
- [ ] Per-package policy override file support for known edge cases (e.g., native compile)
- [ ] Failure triage template: violation log, policy used, package metadata

#### Package Matrix Structure (example)

| Ecosystem | Count | Examples | Pass criteria |
|-----------|-------|----------|---------------|
| pip | 40 | `requests`, `numpy`, `django`, `cryptography` | exit 0, no violations |
| uv | 20 | same set via `uv pip install` | exit 0, no violations |
| npm | 40 | `lodash`, `react`, `esbuild`, `sharp` | exit 0 or documented allowlist |

#### Acceptance Criteria

| # | Criterion | Verification |
|---|-----------|--------------|
| AC1 | Matrix covers ≥100 unique packages across 3 ecosystems | YAML count check |
| AC2 | ≥90% pass rate on Linux CI with default policy | Weekly workflow |
| AC3 | Failures produce actionable report (package, error, suggested policy tweak) | Artifact upload |
| AC4 | Matrix runtime ≤60 min with 4 parallel workers | CI timing |

#### Dependencies

- M1 violation reporting for failure diagnosis
- Sufficient CI minutes / self-hosted runner option for long matrix

#### Risks

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| Flaky network during install | Medium | Retry 2×; cache wheels/node_modules |
| Native compile packages fail under ro-bind | High | Per-package `allow_write_paths` policy extension |
| Matrix maintenance burden | Medium | Auto-generate from PyPI/npm download stats quarterly |

**Estimate:** 2 weeks (initial matrix) + ongoing curation

### Milestone M5 — npm Allowlist Integration (v0.5.0)

**Goal:** Align with npm 12 install-script governance — installfence wraps only allowlisted lifecycle scripts or integrates with npm's approval flow.

#### Deliverables

- [ ] Detect npm ≥12 and read install-script allowlist config
- [ ] `installfence npm` respects npm's blocked/approved script state
- [ ] `--npm-wrap-scripts always|allowlisted|never` policy flag
- [ ] Hook into `npm install` pre/post script phases with sandbox
- [ ] Document integration with `.npmrc` `install-strategy` settings
- [ ] Integration tests with npm 12 fixture project (approved vs blocked scripts)

#### Acceptance Criteria

| # | Criterion | Verification |
|---|-----------|--------------|
| AC1 | Blocked npm scripts never execute (npm native behavior preserved) | npm 12 fixture test |
| AC2 | Approved scripts run inside installfence sandbox | Violation + success test |
| AC3 | `allowlisted` mode only sandboxes scripts npm would run | Matrix sub-suite |
| AC4 | README documents npm 12 + installfence recommended setup | Doc review |

#### Dependencies

- npm 12+ for allowlist semantics
- M1 violation reporting
- M3 shims (optional but recommended for transparent npm wrapping)

#### Risks

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| npm allowlist API changes | Medium | Pin npm version in tests; follow RFC/issues |
| Users expect installfence to replace npm allowlist | Low | Clear docs: complementary, not replacement |
| pnpm/yarn different script models | Medium | Scope M5 to npm; track pnpm/yarn as v0.6 |

**Estimate:** 1.5–2 weeks

## 6. Out of Scope (Deferred)

- Windows native sandbox (non-WSL)
- GUI / IDE plugins (VS Code, JetBrains)
- Hosted SaaS policy management
- Automatic policy generation from ML analysis of install scripts
- Container-only mode (Docker/Podman as primary backend)
- Package reputation scoring / blocklisting
- Integration with OS-level mandatory access control (AppArmor/SELinux profiles)
